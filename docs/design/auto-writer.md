# 自动写小说：终局设计

> 状态：**设计已定，前几步已落地**（进度见文首「实施进度」；第 4 步起仍未实现）。
> 本文记录 2026-10-14 那轮盘问的全部结论、以及每条结论的来源。
> 参考项目：[`CyrilPeng/novel-auto-generator`](https://github.com/CyrilPeng/novel-auto-generator)（SillyTavern 扩展，自动续写）、
> [`flizzywine/dsh-tavern`](https://github.com/flizzywine/dsh-tavern)（DSH 酒馆，同类架构）。
>
> **读本文前须知**：本设计**一次真实模型会话都没跑过**（见「未验证的假设」）。凡标注 ⚠️ 的都是推断，不是实测。
>
> 实施进度：§10 的第 1–3 步已落地（三个可选字段 + 大纲第一层进系统提示词 + `goal` 进简报；
> `novel_project` / `novel_chapter` 的写入通道；两个入口**技能** `novel-plan` / `novel-quick`）。
> 第 3 步与本文原稿有一处**有意的偏离**：
> 入口做成了 SKILL.md 而**不是**命令处理器——命令不经过模型、只能返回文本，而这两个入口要让模型去做事。
> 第 4 步起（后台 agent / `create_goal` 循环 / 检索 / 候选池筛选）仍未实现。

---

## 1. 目标

插件从"**辅助人写小说**"转向"**自动写小说**"：给一个大纲与章节数，它自己一章接一章写到完。

现状与目标的差距：现有 8 个工具、50 个动作**全是原子操作**（写一章、记一条设定），
**没有任何"写到第 20 章为止"的驱动**，也没有大纲这个概念。

---

## 2. 设计原则（来自 dsh-tavern，两条都推翻了我们的初版）

### 2.1 混合上下文供给（Hybrid Context Supply）

> 程序负责**高确定性、低成本、不可遗漏**的上下文；
> Agent 负责**开放、长尾、难以预判**的上下文。

程序组装的优势（不是缺点，别丢）：可控可调试、毫秒级、**不增加模型往返**、不会遗漏。
Agent 检索不是免费的：多一次工具往返、多一份 token、多一层行为不确定性。

**这条判据直接决定每一层信息走哪条路。**

### 2.2 正文是独立的提交边界

> 正文成功后立即建立 checkpoint；**后续状态结算失败不能撤销正文**，也不能阻止下一轮。
> operation 只有排队、运行、完成、失败、过期或取消等生命周期事实。

映射到本插件：

| 事件 | 是不是事务提交 |
|---|---|
| 一章正文落盘（`novel_chapter action=append`） | **是**，提交即定 |
| 自检 / 摘要 / 词条更新 | **否**，提交后的派生工作 |
| 自检没过 | **重写这一章**（正文尚未算作完成），但**不回滚已有章节** |
| 后台记账失败 | **不阻塞下一章** |

**结论：停下来的条件是"正文没写出来"，不是"检查没过"。**

## 3. 决策清单

| # | 决定 | 来源 |
|---|---|---|
| 1 | 面向**公开发布**（要 npm、文档、向后兼容） | 用户 |
| 2 | 用户**显式选模式**：`/novel-quick`（直接写）· `/novel-plan`（先大纲等确认） | 用户；不猜阈值 |
| 3 | **两阶段：先大纲后正文** | 用户；大纲阶段是**唯一便宜的人工介入点** |
| 4 | 大纲**分三层** | 见 §4；用 §2.1 判据验证过 |
| 5 | 驱动走**会话内自动续跑**（`create_goal` / `goal-round-driver`） | 用户；已核实这些工具在组合里是启用的 |
| 6 | **前台写正文，后台干杂活**（自检/摘要/词条） | 用户；来自 dsh-tavern 的核心拆分 |
| 7 | 后台是**一个对话级持久 agent**，任务以不同 operation 提交 | dsh-tavern ADR-0002；一致性（词条别越记越乱）比性能更重要 |
| 8 | 跨章记忆 = **近章给尾部原文（Push）+ 更早的靠检索原文（Pull）** | **推翻初版**：原计划"每章存摘要注入简报"被 dsh-tavern 否定 |
| 9 | 写崩了：**自检 + 重试，连败就停**（按 §2.2 的口径） | 用户 + §2.2 修正 |

### 3.1 第 8 条为什么改（重要）

原计划：每章存摘要，写第 N 章时把前几章摘要注入简报。

dsh-tavern 的原文否定了这个做法：

> **完整保存正文**：历史原文是权威信息源，**不用变量、摘要或数据库记录取代它**。
> **不预测未来需求**：不把大量摘要固定回灌上下文。

理由（我们自己的补充）：**摘要是有损的，而且写砸了就真丢了**——原文还在，但你不知道摘要漏了什么。
对比之下，"检索原文"是可搜索、可反复读、可核对的。

**但保留 Push 的那一半**：上一章尾部原文仍然自动带（"不可遗漏"），更早的才交给检索。

## 4. 大纲三层（**已定**）

| 层 | 存哪 | 放什么 | 归类 | 为什么 |
|---|---|---|---|---|
| 一 | `project.json` 加 `outline` 字段 | 全书梗概 300–800 字 | **Push** | 进系统提示词 → **每章自动带上**；不可遗漏 |
| 二 | `outline.md` 单文件 | 细纲：分卷/分幕、伏笔埋设与回收、关系变化 | **Pull** | 太长不进简报；写第 7 章不需要第 40 章的细节，**按需 `read`**（首方工具即可，不新增工具） |
| 三 | `ChapterMeta` 加 `goal` 字段 | 每章一句"这章推进什么" | **Push** | 一行，便宜且必须给 |

**技术约束（已核实）**：`buildSystemPrompt(project, characters, contextText, preset)` **收不到章节元数据**
（`src/domain/prompt.ts`）。所以每章 `goal` 需要**单独加一条通路**进简报，不能指望它搭系统提示词的便车。

**第一层已实现**：`PromptProject.outline` 非空时，`buildSystemPrompt` 在
`## 作品简介` 之后、`## 世界观与背景` 之前推一个独立区块 `## 全书大纲\n<梗概>`，且**无条件附带**
——它刻意放在 `preset.storyString` 的 if / else **之外**。理由是两者的性质不同：预设的 story_string
管的是**文风与设定怎么呈现**，而全书大纲是**这本书的事实**，属于本表第一行的「不可遗漏」层，
不能被一个没引用它的模板悄悄丢掉。`outline` 为空（含老作品的缺失）时输出与实现前**逐字相同**。
（易混点：第一层只有 300–800 字，**不是** `outline.md`——第二层才是"太长不注入"的那一层。）

第二层的形态借鉴 dsh-tavern 的「剧本模式」：**按片段读，再长也不用整本塞进上下文**。

## 5. 写作流程

### 5.1 `/novel-plan`（先大纲）

```
1. 建/选作品
2. 产出三层大纲：project.outline + outline.md + 每章 goal
3. 停下来给人看 —— 改大纲远比改已写好的章节便宜
4. 确认后 → 转 5.2
```

### 5.2 自动写（两个入口共用）

```
create_goal("写完全部章节")                    ← 打上目标，跨轮次自动继续
每章：
  1. novel_context chapter=N                  ← 取简报（程序 Push：全书大纲/概要/命中词条/角色/预设/前章尾部/goal）
  2. （可选）novel_recall 检索更早的原文        ← Agent Pull，见 §7 未决
  3. 写正文 → novel_chapter action=append      ← ★ 事务提交点
  4. 提交后派生工作（同一个持久后台 agent）：
     - 自检：字数够吗？推进了 goal 吗？与前文矛盾吗？
     - 不合格 → 重写这一章（不算提交）
     - 连败 N 次 → 停下来问人
     - 合格 → 写摘要（供检索用，不注入）、更新词条
```

### 5.3 `/novel-quick`（直接写）

跳过 §5.1，直接进 §5.2。适合**没有贯穿性线索**的作品（单元剧/日常）。
短篇也走这条——**判据不是长短，而是"这本书有没有需要收束的伏笔/主线/关系弧"**；
但因为是用户显式选模式，工具不必去猜。

## 6. 数据模型改动

| 位置 | 新增 | 用途 |
|---|---|---|
| `project.json` | `outline?: string` | 全书梗概（Push） |
| `outline.md` | 新文件 | 细纲（Pull）；不存在时一切照常 |
| `ChapterMeta` | `goal?: string` | 每章目标（Push） |
| `ChapterMeta` | `summary?: string` | 每章摘要——**供检索结果展示，不注入简报** |

**兼容性**：全部可选字段。老作品缺这些字段必须照常工作（这个仓库对"损坏/缺失数据"的既有口径是**点名而不是静默当空**，新字段要沿用）。

## 8. 从 dsh-tavern 蒸馏出来的机制（可直接用）

详细出处见 `flizzywine/dsh-tavern` 的 `docs/design/*` 与 `docs/plugin-api.md`。

### 8.1 ★ 候选池筛选：本地召回 + 后台筛选，且**只能删不能加**（治"词条注入不准"）

它已实现的机制（`docs/design/worldbook-recall.md`）：

| 环节 | 谁做 | 特性 |
|---|---|---|
| 关键词扫描 / 递归 / 包含组 / 冷却 | **本地确定性** | 毫秒级、可调试、不花 token、不会遗漏 |
| 候选池**超过 5 条或渲染超 2000 token** 时 | **持久后台 Agent 筛选** | 权限收窄 |

关键在**权限边界**：

> 筛选**可以全部排除，但不能添加池外条目**；常驻与脚本明确调度的条目不交给筛选。

**为什么这条对我们重要**：现有 `selectLoreEntries` 是"关键词命中即注入"，**没有任何机制能说"这 30 条里只有 5 条真的相关"**。
AGENTS.md 自己记着这个坑（`keys=",,"` 拆成空数组会退化成**常驻注入**，每回合全文进提示词）。

**为什么"只能删"是对的**：漏注入会丢设定、糊注入会浪费上下文，两者严重性不对称。
本地负责召回（保证不漏），Agent 负责筛选（保证不糊），且**只给减法权限**——这是安全的方向。

### 8.2 Skill 按 Agent 角色分配（引入后台 agent 后**必须**做）

它把 Skill 分成**卡片 Agent / 前台 Agent / 后台 Agent** 分开分配，用户可覆盖默认（`docs/design/writing-style-skills.md`）。

**现状问题**：本插件 8 个技能是**平的**（全 rank 250，谁都能看见）。
引入后台 agent 后不改，后台记账时会被塞一嘴文风技巧——正是它说的"注意力涣散"。

预期分区：`novel-prose` / `novel-dialogue` / `novel-scene` → **前台**；
`novel-cards` / `novel-writing` → 前后台都要；自检/记账规则 → **后台**。

### 8.3 参考材料延迟加载（我们第二层大纲的同构做法）

Skill 本体精简，细节放 `references/*.md`，用只读工具**按需读**（同上文档）。

这与本文 §4 的第二层（`outline.md` 按需 `read`）**是同一个模式**——互为佐证。

### 8.4 生态与分发（面向"公开发布 + 让别人写插件"）

`docs/plugin-api.md` 的三条承诺，是"要生态"的范本：

| 承诺 | 内容 |
|---|---|
| 方便 | 插件不改源码、不读数据文件、不打补丁 |
| 稳定 | 接口带版本号，**只加不改**，废弃至少保留 6 个月 |
| 自由 | 挂什么/何时/几个/用什么模型，全由插件定 |

**失败隔离**（直接对上我们踩过的坑）：

> 多数是**添加类**接口，插件出错**只会丢掉它自己那一份**，游戏照常进行；
> 少数**替换类**接口，插件失败时**自动退回**宿主自己的做法。

对比本插件的客户端半边是 **fail-closed**（一个包缺产物 → **所有**客户端插件一起挂）。
它能隔离失败，靠的是**插件放进 `plugins/` 目录即加载、失败只记日志**（运行时加载 + 容器化），
而不是静态扫描。**代价**：插件代码跑在宿主进程里，安装插件 = 执行任意代码，需要完全权限。

两条现成机制：

- **`package.json` 的 `dsh.compatibility`**（`dsh-tavern-image` 在用）：声明支持的 DSH 版本区间，
  不匹配时给明确提示。本包**没有**这个字段（我们靠 `src/harness.ts` 运行期自证版本，是另一条路）。
- **规则即数据**：`dsh-tavern-image` 把生图规则同时做成"给人改的 `.md`"与"给模型读的世界书条目"，
  条目内容写的是**踩过的坑 + 理由**（例："负面绝不能出现 loli，那会直接把角色特征压掉"）。

### 8.5 明确**不**参考的

它实现了完整的 SillyTavern 世界书语义：`scan_depth`、四种副关键词逻辑（AND_ANY / NOT_ALL / NOT_ANY / AND_ALL）、
递归扫描与四种守卫（`preventRecursion` / `excludeRecursion` / `delayUntilRecursion`）、
包含组权重抽选……实现度很高，但**本插件不是酒馆兼容产品**。
**该抄的是 §8.1 的架构（本地召回 + 受限筛选），不是它的关键词复杂度。**

## 9. 未验证的假设（⚠️ 全部是推断）

**本设计建立在从未观察过的行为上。** 现有验证全部在工具层：

| 假设 | 为什么危险 |
|---|---|
| ⚠️ 模型会**主动**调 `novel_context` | 它不调，整个简报设计就是空转 |
| ⚠️ 简报的**信息量够** | 够不够只有真实文本能回答 |
| ⚠️ 模型会**老实自检** | 自检是整个质量门的唯一依靠 |
| ⚠️ 模型会**在该停的时候停** | 不停就是无限重写同一章 |
| ⚠️ `create_goal` 的自动续跑在长任务上**可靠** | 没试过连写 20 章 |
| ⚠️ 模型会**主动用检索**找前文 | 不检索就等于没有跨章记忆（dsh-tavern 用"工具常驻在稳定前缀"来保证它会用） |

**建议：动 §10 任何一条之前，先花一次会话跑一遍现有插件（不改代码）**，
观察模型实际怎么用工具。那一次的观察结果直接决定 §5.2 第 4 步怎么设计——
现在设计它**是在猜**。

## 10. 实施顺序（按依赖，不按吸引力）

| 步 | 内容 | 依赖 |
|---|---|---|
| 1 | 数据层：`outline` / `goal` / `summary` 三个可选字段 + 缺失容忍 | 无 |
| 2 | 简报扩展：`outline` 进系统提示词（§4 第一行的 Push 口径）、`goal` 进简报的新通路；尾部摘录口径不变 | 1 |
| 3 | 两个入口（**已按技能实现**，不是命令：命令不经过模型）：`/novel-plan`、`/novel-quick` | 1 |
| 4 | 后台持久 agent：自检 / 摘要 / 词条更新（按 §2.2 的事务边界） | 2 |
| 5 | Skill 按角色分配（§8.2）——**第 4 步一落地就必须做，否则后台被文风技巧污染** | 4 |
| 6 | 候选池受限筛选（§8.1）——治词条注入不准 | 4 |
| 7 | `create_goal` 驱动的写作循环 + 重试上限 | 3、4 |
| 8 | （未决后定）检索能力 | 见 §7 |
| 9 | 公开分发形态 + `dsh.compatibility` | 见 §7 |

**第 7 步之前必须先做 §9 的那次真实会话观察。**
